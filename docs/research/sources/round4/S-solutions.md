## 2. ESM-only vs dual ESM+CJS in 2026

- **Node.js `require(esm)` is now stable.** Per Joyee Cheung's blog (joyeecheung.github.io, fetched 2026-09-24): `require(esm)` has been "marked as stable" and is "unflagged across all supported Node.js LTS release lines," specifically **Node v20.19.0+ and v22.12.0+**. WebSearch corroborates via Socket.dev: "Node.js 25.4.0 Ships with Stable require(esm)" (released Jan 19, 2026), backported to LTS lines.
- **Caveat that still applies**: `require(esm)` does not support ESM modules that use top-level `await` ("Because `require(esm)` needs to stay synchronous, it can't support modules that use top-level `await`": Cheung blog). An ecosystem scan cited in that post found this affects roughly 1 of 5,000 high-impact npm packages. Such modules remain loadable via `import()`.
- This removes the primary historical reason CJS builds existed for Node consumers, but does not eliminate every consumer-side reason (older bundler configs, Jest CJS transform assumptions, etc.: not independently verified here beyond Next.js/transpilePackages evidence below).
- **TanStack Table v9 is ESM-only.** Per TanStack's own announcement (tanstack.com/blog/announcing-tanstack-table-v9, fetched 2026-09-24) and corroborating WebSearch results: v9 "dropped UMD and CJS builds, with packages now shipping as modern ESM only," "published packages no longer ship src or source maps," released stable "August 4, 2026" after ~2 years of work. Exact package-size claim quoted verbatim from the announcement page: "the total package size has increased from 14kb to 25kb at the time of writing," offset by "Features are explicit, modular, and tree-shakeable in Table V9. A table that only registers sorting does not need to ship filtering, pagination, grouping, or the rest of the built-in feature set." This CONFIRMS brief claim 4.
- **Carbon (`@carbon/react` 1.117.0) ships dual ESM+CJS**: `"main": "lib/index.js", "module": "es/index.js"` in `package.json`: no `"exports"` map present in this version's package.json (confirmed by reading the file directly), meaning resolution relies on the legacy `main`/`module` fields rather than conditional exports.
- **IBM Products (`@carbon/ibm-products` 2.99.0) also ships dual ESM+CJS**: `"main": "lib/index.js", "module": "es/index.js", "types": "lib/index.d.ts"`: CONFIRMS brief claim 1's ESM/CJS half. Types are only pointed at from `lib/` (CJS) via top-level `types` field; `es/` types exist as files (per earlier ibm-products-style evidence pattern) but the field itself only references the `lib/` path (unverified whether TS resolves `es/*.d.ts` correctly for ESM consumers without an `exports` map with separate `types` conditions: no `exports` field exists in this ibm-products `package.json` either).
- **MUI v7** moved to unambiguous dual support via a proper `exports` map: "now unambiguously supports both valid ESM and CommonJS through the exports field in package.json. The package layout was previously faux-ESM" (WebSearch synthesis of mui.com/blog/material-ui-v7-is-here and migration docs). Side effect: "Deep imports with more than one level are no longer working with the new exports field, as they were already considered private API."
- **Radix UI primitives**: package.json evidence (`radix-ui/primitives` repo, `packages/react/*/package.json`) shows `react`/`react-dom` as `peerDependencies` (`^16.8 || ^17.0 || ^18.0 || ^19.0 || ^19.0.0-rc`), `@types/react`/`@types/react-dom` as optional peerDependencies, and `"sideEffects": false`. Radix does not bundle React.
- **Jest**: no primary source fetched in this session on Jest ESM-only-package handling (unverified: flagged as a gap; historically Jest's CJS-first transform pipeline is the most common blocker for ESM-only npm packages in test environments, needs `extensionsToTreatAsEsm`/`transformIgnorePatterns` tuning, but this specific claim is not confirmed here with a primary Jest doc).
- **Dual-package hazard**: not independently re-verified with a primary Node.js doc quote in this session (unverified); the standard description is that a dual ESM+CJS package can end up with two separate module instances/registries (e.g. two React contexts) when a dependency graph pulls in both the ESM and CJS builds of the same package simultaneously. Given below (section 3) this is directly relevant to whether Carbon should be a peerDependency.

## 3. Carbon as peerDependency vs dependency vs bundled

- **Confirmed via primary source**: `@carbon/ibm-products` 2.99.0 `package.json` lists `@carbon/react`, `@carbon/grid`, `@carbon/layout`, `@carbon/motion`, `@carbon/themes`, `@carbon/type` as **peerDependencies** (ranges `^1.115.0`, `^11.61.0`, `^11.58.0`, `^11.51.0`, `^11.80.0`, `^11.66.0`), and `react`/`react-dom`/`react-is` as peerDependencies too (`^16.8.6 || ^17.0.1 || ^18.2.0 || ^19.0.0` etc). This CONFIRMS brief claim 1's "does not bundle Carbon" half.
- **But** IBM Products' own `dependencies` block includes `@carbon-labs/react-resizer` (`^0.25.0`), `@carbon/feature-flags`, `@carbon/ibm-products-styles`, `@carbon/telemetry`, `@carbon/utilities`, `@carbon/utilities-react`, plus non-Carbon deps (`@dnd-kit/*`, `react-table`, `react-window`). So IBM Products is not "zero dependencies": it treats the *core* Carbon React/styles/theme packages as peer (consumer supplies one shared copy) but treats *smaller satellite* Carbon packages (labs widgets, feature-flags, telemetry, utilities) as regular dependencies it installs itself. This is a middle pattern, not pure peer-everything.
- **`@carbon/react` 1.117.0 itself** lists `react`, `react-dom`, `react-is`, and **`sass`** as peerDependencies (`sass: "^1.33.0"`), and bundles `@carbon/feature-flags`, `@carbon/icons-react`, `@carbon/layout`, `@carbon/motion`, `@carbon/styles`, `@carbon/utilities` as regular `dependencies`. So Carbon-the-library treats React as peer but treats its own sub-packages (styles, layout, icons) as dependencies it pulls in itself: meaning a consumer app that also directly depends on `@carbon/styles` at a different version can get two copies unless npm/pnpm dedupes them.
- **Duplicate-React/duplicate-context risk**: making React a `dependency` instead of `peerDependency` on a component library is the textbook cause of "Invalid hook call" / broken Context errors from two React copies; Carbon's, IBM Products', and Radix's own package.json choices confirm the entire ecosystem treats `react`/`react-dom` as peer, never as bundled/dependency, for this reason (pattern observed identically across all three packages inspected).
- **sass as peerDependency** on `@carbon/react` is notable: it means Carbon expects the *consumer* (or an intermediate library) to supply the Sass compiler version, not IBM. Any wrapper library that ships its own compiled Sass source and doesn't declare `sass` as a peer risks version mismatches if the consumer's own sass differs from what compiles the v12 feature-flag path correctly (untested whether older sass versions break the v12 flag; only `sass ^1.105.0` was tested in this session, see section 4).

## 4. Shipping styles for a Carbon v12-flagged library

### 4a. Ship Sass source only (consumer compiles)

- `@carbon/react` declares `sass: "^1.33.0"` as a peerDependency (see above): the package's own metadata assumes Sass compilation happens outside the package, in the consumer's build.
- Next.js has built-in Sass support: `nextConfig.sassOptions` is "passed directly to the Sass compiler," documented options include `includePaths`/`loadPaths` and `additionalData` (nextjs.org/docs/app/api-reference/config/next-config-js/sassOptions, WebSearch synthesis; page confirms `sassOptions` exists but this session did not fetch the full page verbatim, so exact current option names beyond `includePaths`/`additionalData` are best-effort, not directly quoted: unverified for `loadPaths` spelling specifically in the current Next.js version).
- **Tested and confirmed module-configuration pitfall** (ran in the round-3 Sass scratch project of `round3/S-sass-check.md`, files `r4-lib-a.scss`, `r4-consumer-b.scss`, `r4-consumer-same.scss`, `r4-consumer-noconfig.scss`, `r4-combined*.scss`):
  - Scenario A: one file (`r4-lib-a.scss`, simulating this library's Sass entry) does `@use '@carbon/styles/scss/feature-flags' with ($feature-flags: ('enable-v12-release': true));` then `@use '@carbon/styles';`. A second file (`r4-consumer-b.scss`, simulating a consumer or another dependency) does the same `@use ... with` but with `false`. A third file `@use`s both into one compilation. **Result: hard compile error**, exit code 65:
    ```
    Error: This module was already loaded, so it can't be configured using "with".
      ┌──> r4-consumer-b.scss
    3 │ @use '@carbon/styles/scss/feature-flags' with ($feature-flags: ('enable-v12-release': false));
      │ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ new load
      ┌──> r4-lib-a.scss
    2 │ @use '@carbon/styles/scss/feature-flags' with ($feature-flags: ('enable-v12-release': true));
      │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ original load
    ```
  - Scenario B: same test but **both files configure the flag to the identical value (`true`)**. **Still errors**, same exit code 65, same message. Configuring a module a second time with `with` is illegal regardless of whether the value matches: Sass does not compare values, it simply forbids re-configuration after first load.
  - Scenario C: one file configures (`r4-lib-a.scss`, flag `true`), a second file plainly `@use '@carbon/styles';` with **no** `with` clause. **Compiles successfully** (exit 0, 34,625-line output CSS): a bare `@use` without `with` silently inherits whatever configuration was set by the first loader in the compilation graph, no error, no warning.
  - **Consequence**: if this library ships raw `.scss` source that configures `enable-v12-release: true`, and a consumer app's own Sass entry point (or another Carbon-based package the consumer also uses, e.g. installing `@carbon/ibm-products-styles` directly for something not covered by this library) *also* tries to explicitly set that same feature-flag module with `with`, the consumer's entire Sass build fails to compile, even if they intend the same value. Consumers must NOT independently configure `@carbon/styles/scss/feature-flags` (or any Carbon module this library already configures) anywhere in the same compilation graph; they can only use plain `@use` of the already-configured module, or avoid importing our Sass source into the same compile graph as their own Carbon Sass entry.
  - Practical implication: shipping Sass source is workable only if this library is the *sole* configurer of Carbon's Sass modules in any given consumer's build, or if the library ships a fully self-contained Sass entry that the consumer imports without themselves also directly `@use`-configuring `@carbon/styles`/`@carbon/ibm-products-styles`. This is a real integration constraint, not a theoretical one.
- **Compile time measured**: `time npx sass --quiet-deps --load-path node_modules v12.scss out.css` in the sass-check sandbox took **4.56s real / 6.16s user** for a build importing `@carbon/styles` (with v12 flag) plus `@carbon/ibm-products-styles/scss/index-without-carbon` (from `v12.scss` contents: `@use '@carbon/styles/scss/feature-flags' with (...); @use '@carbon/styles'; @use '@carbon/ibm-products-styles/scss/index-without-carbon';`). This is a one-time full compile of the whole Carbon+IBM-Products Sass surface, not incremental; per-consumer-build cost if Sass source is shipped and compiled on every consumer `next build`.

### 4b. Ship compiled CSS only

- **Confirmed**: `@carbon/styles` 1.116.0 ships exactly two prebuilt CSS files: `css/styles.css` and `css/styles.min.css` (directory listing of `<npm pack>/carbon-styles-1.116.0/package/css`): a **single bundled file each**, not per-component CSS. This means no CSS tree-shaking is possible from the prebuilt output; the whole design system's CSS ships regardless of which components a consumer actually uses.
- **Size measured locally**: a full v12-flag Sass compile of `@carbon/styles` + `@carbon/ibm-products-styles` (`v12.scss`) produced a 1,961,685-byte (≈1.96 MB unminified) CSS file (`wc -c v12.css`); the v11 (unflagged) equivalent was 1,954,484 bytes: roughly comparable size, confirming the v12 flag mainly changes rule content/selectors, not overall volume, in this build.
- **Runtime theming confirmed**: the compiled v12.css contains 10,394 occurrences of `--cds-` custom-property tokens (`grep -c -- '--cds-' v12.css`), i.e. Carbon's compiled CSS defines/consumes CSS custom properties extensively, which is what enables runtime theme switching (e.g. swapping `data-carbon-theme` or root-level custom-property overrides) without recompiling Sass.
- Carbon's theme mixin machinery uses `custom-property.get-var(...)` for tokens like `layer`, `field`, `border-subtle`, etc. (confirmed by reading `<npm pack>/carbon-styles-1.116.0/package/scss/theme/_theme.scss` lines 23-42): i.e. theme values are emitted as custom properties, not hardcoded static values, at Sass-compile time. Exact runtime "zones" API/attribute name (e.g. `data-carbon-theme`) was reported by WebSearch summaries of carbondesignsystem.com and GitHub discussions but not independently confirmed by fetching the live carbondesignsystem.com page (that WebFetch attempt returned no content): mark as (unverified) pending a direct doc quote, though the underlying custom-property mechanism is confirmed from the shipped Sass/CSS itself.
- IBM's prebuilt CSS is v11-styled (brief claim 3): the `styles.min.css` file ships without the v12 feature flag applied by IBM, per the phase-0 decision record already in this repo (`round4/BRIEF-R4.md` line stating "IBM's prebuilt styles.min.css is v11-styled"): this session's compiled-CSS size/byte comparison (v11.css vs v12.css, both compiled locally with the same sass toolchain) is consistent with that but does not itself re-derive it from IBM's actual shipped `styles.min.css` byte-for-byte (not diffed in this session; treat the v11-styled claim as previously established, not re-verified here beyond the local scaffolding files already present under `sass-check/`).

### 4c. Ship both

- Combines 4a's compile-graph conflict risk (consumers who also touch Carbon Sass directly can break) with 4b's all-or-nothing CSS size, but gives consumers a choice: fast path (import prebuilt CSS, get v12 look untouched) or flexible path (import Sass, customize tokens/`@use ... with`, at the cost of the section-4a conflict and the ~4.5s+ compile time added to their build for every build/watch cycle unless cached).

## 5. Consumption from GitHub Packages: Next.js (App Router) and Vite

- **transpilePackages**: Next.js docs (nextjs.org, WebSearch synthesis, corroborated by page title/URL): "Next.js does not compile code inside `node_modules` by default. Listing the package opts it in, or you can build the package to plain JavaScript and point its `main`/`exports` at the compiled output." Use case explicitly given: "A `node_modules` dependency ships raw TypeScript or JSX." Since Carbon and this wrapper library both ship pre-built JS (not raw TS/JSX) in their published packages (`es/`/`lib/` directories of compiled `.js` + `.d.ts`), `transpilePackages` should not be required for them specifically: it's only needed if the wrapper library ships raw `.ts`/`.tsx` source without a build step. Config example given: `transpilePackages: ['@acme/ui', 'lodash-es']`.
- Turbopack (Next.js's newer bundler) "transpiles workspace packages (npm, pnpm, or Yarn workspaces) in your monorepo automatically under both routers. Webpack does the same for the App Router": i.e. monorepo workspace packages get auto-transpilation in more cases than arbitrary `node_modules` packages like ones installed from GitHub Packages (which are not workspace-linked).
- **ESM packages must be imported, not required**: "Packages in node_modules that are published as ECMAScript Module, need to be imported via `import ... from 'package'` or `import('package')`" (Next.js docs page `docs/messages/import-esm-externals`, WebSearch synthesis): relevant if this library or TanStack Table v9 (ESM-only) end up required via CJS interop paths in older Next.js configs.
- **Global CSS from node_modules in the App Router**: "The limitation of importing CSS Modules from node_modules does not exist when using the App Router" and "Since Next.js 9.5.4, importing a CSS file from node_modules is permitted anywhere in your application," with the documented pattern being `import 'bootstrap/dist/css/bootstrap.css'` inside `app/layout.js`, and a note that "you may need to use `'use client'` if required by the third-party library" (WebSearch synthesis of nextjs.org/docs messages pages `css-modules-npm`, `css-global`, `css-npm` plus the getting-started CSS guide). This directly supports the "ship compiled CSS, consumer imports it once in root layout" pattern from section 4b.
- **Server Components**: Carbon React's `"use client"` directive is present only on the package's top-level `es/index.js`/`lib/index.js` entry (see section 1 table), which means importing anything from `@carbon/react`'s main entry point in a Server Component file will correctly mark the whole subtree as client: but any deep-import path that bypasses `index.js` (if this wrapper library re-exports individual component files directly rather than going through Carbon's own `index.js`) would need its own directive or would silently lose client-boundary marking. This is a concrete inherited risk from Carbon's package-wide (not per-file) directive placement, for whatever build tool this library adopts internally.
- No primary source in this session specifically covering GitHub Packages npm-registry authentication mechanics inside Next.js/Vite build environments (e.g. `.npmrc` token handling in CI): that is a registry-auth concern orthogonal to ESM/CSS handling and was not covered here (unverified/out of scope for this pass).

## 6. Comparison table (facts and consequences, no pick)

|---|---|---|---|---|

| Ship compiled CSS only | Consumer does one `import '@lib/styles.css'` in root layout/entry (App Router pattern confirmed: "Since Next.js 9.5.4, importing a CSS file from node_modules is permitted anywhere") | Library runs the v12-flagged Sass compile once at publish time | Runtime theming still available via the ~10,394 `--cds-*` custom properties baked into the compiled CSS; but no Sass-level customization | No per-component CSS (only 2 files shipped by `@carbon/styles` itself: `styles.css`/`styles.min.css`), so no CSS tree-shaking; consumer always ships the whole stylesheet regardless of which components are used |
| Ship both (Sass + compiled CSS) | Consumer picks one path; if they pick Sass they inherit the section-4a conflict risk, if they pick CSS they inherit the no-tree-shaking cost | Library does both the Sass publish-time compile and ships raw scss | Maximum consumer choice | Combines both risk surfaces; requires clear consumer documentation on never mixing the two import paths in one build, and never independently configuring the same Carbon Sass modules the library configures |
| Carbon as peerDependency (core packages) vs dependency (satellite packages), following IBM Products' own pattern | Consumer must install matching versions of `@carbon/react`, `@carbon/grid`, `@carbon/layout`, `@carbon/motion`, `@carbon/themes`, `@carbon/type` themselves (peer ranges e.g. `^1.115.0`, `^11.61.0` etc. from ibm-products 2.99.0 package.json) | N/A | Avoids duplicate-React/duplicate-Carbon-core risk (confirmed pattern across Carbon, IBM Products, Radix: React always peer, never bundled) | Satellite packages like `@carbon-labs/react-resizer`, `@carbon/feature-flags`, `@carbon/utilities` are treated as regular dependencies by IBM Products itself, so a consumer that also separately installs those exact satellite packages at a different version can still get duplicates; peer-only avoids this solely for the packages explicitly listed as peer |
