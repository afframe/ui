# 01 · Carbon core and foundation packages
Retrieved: 2026-09-23 · Lane: core

## Summary (5-10 bullets)

- Carbon lives in one monorepo, `github.com/carbon-design-system/carbon` (Apache-2.0, 9,484 stars, actively pushed same day as retrieval). Packages are layered: **Layer 0 "Elements"** (colors, grid, icons, pictograms, layout, motion, themes, type — near-zero internal deps) → **Layer 1 "Primitives"** (styles, icons-react, icons-vue, pictograms-react, upgrade, utilities, utilities-react) → **Layer 2 "Components"** (`@carbon/react`, `@carbon/web-components`), which re-export the lower layers so most consumers only need to install the top-level package. [Source: docs/package-structure.md]
- `@carbon/react` is versioned 1.x on npm (currently 1.117.0) but is documented and marketed as "v11" — the "11" refers to the overall Carbon *design system* major generation, not the npm semver major of the React package; npm semver major/minor/patch follow a documented policy (docs/guides/versioning.md) independent of the "v11" branding. Confirm this mapping is intentional and not a scope gap — it is a common source of confusion. [Source: 00-inventory.json; docs/guides/versioning.md]
- Carbon uses biweekly minor releases while in the "Active" phase; v11 is Active (initial release 2021-08-06, began Active 2022-03-31, maintenance TBD); v10 reached end-of-life 2024-09-30; v12 is in "Preview" (opt-in via `enable-v12-*` feature flags) since 2023-05-25 with no committed Active/GA date yet. [Source: docs/release-schedule.md]
- Component maturity is signalled two ways: (1) a `preview_` export prefix (formerly "experimental"/"unstable_") for whole components/APIs not yet stable, and (2) `enable-*` / `enable-v12-*` Sass+React+Web Components feature flags for opt-in behavior changes, the latter becoming default-on in the next major (v12). [Source: docs/preview-code.md; docs/feature-flags.md]
- Styling requires Dart Sass and the Sass **module system** (`@use`, not `@import`); `$prefix` (default `cds`) controls all selector/CSS-custom-property prefixing; per-component Sass entry points allow selective `@use '@carbon/styles/scss/components/button'` imports to reduce compiled CSS size; a precompiled `@carbon/styles/css/styles.css` also exists for teams that don't want to run Sass. [Source: docs/guides/sass.md; GitHub issue #11599]
- TypeScript types for `@carbon/react` are native `.d.ts` files bundled in the package but the migration from PropTypes is **incomplete** — the README explicitly says "not all components have yet been typed" and recommends `skipLibCheck: true`; a public GitHub Project tracks TS adoption progress. [Source: packages/react/README.md]
- `@carbon/react`'s peerDependencies currently allow React 16.8.6+, 17.0.1+, 18.2.0+, and 19.0.0+ — React 19 is supported today, but two React-19-specific breakage reports (Tabs family, `use-resize-observer`) were filed and only closed/fixed in Feb and May 2025 respectively, indicating the initial React 19 support window had rough edges. [Source: 00-inventory.json peerDependencies; GitHub issues #18574, #19350]
- Carbon components do not ship `'use client'` directives themselves; because nearly all Carbon React components are interactive (hooks/state), consumers using Next.js App Router must add `'use client'` in their own wrapper components — this is documented informally via the community `carbon-tutorial-next` example repo, not an official RSC compatibility statement from Carbon. [Source: github.com/carbon-design-system/carbon-tutorial-next; unverified as an official Carbon RSC support statement]
- Longstanding, still-cited community complaints: Sass compile time/build-time bloat when pulling in the full stylesheet (multiple long-running GitHub issues/discussions, e.g. #3348, #5059, #6198, #7294, discussion #8526), and CommonJS-era tree-shaking limitations (#4881, #4882, #5980) — some of these issues predate the v11 Sass-module rewrite and precompiled-CSS option, so their current severity on `@carbon/react` 1.x is unverified.
- `@carbon/react` embeds **IBM Telemetry** by default (an opt-out anonymized-usage-collection mechanism) — relevant for a source-available, noncommercial-licensed downstream package that itself will be redistributed to other repos. [Source: packages/react/README.md]

[Source: `gh api repos/carbon-design-system/carbon/contents/packages/react/src/components`]
- **Maturity/status mechanism**: components/APIs not yet stable are exported with a `preview_` prefix (e.g. `import { preview_Foo as Foo } from '@carbon/react'`), documented under the "Preview" section of Storybook. This replaced the older "experimental"/"unstable_" naming as part of Carbon's Product Development Lifecycle (PDLC) process. A documented checklist (issue template) governs promotion from preview → stable, requiring ~3 months of real-world feedback, full test coverage (unit, VRT, AVT), Figma Code Connect, and website docs. [Source: docs/preview-code.md, docs/experimental-code.md]
- **Feature-flag mechanism**: two tiers — `enable-*` flags (stable-ish, opt-in previews of new behavior, may still change) and `enable-v#-*` flags (locked API, will ship "on" by default in the named future major, e.g. `enable-v12-overflowmenu`). Flags can apply to React, Sass, and/or Web Components independently and are enabled per-surface: React via a `<FeatureFlags>` wrapper/props, Sass via `@use '@carbon/styles/scss/feature-flags' with ($feature-flags: (...))` or the `enable()` mixin, Web Components via element attributes. `enable-v12-release` turns on every `enable-v12-*` flag at once. Some flags ship an automated codemod via `@carbon/upgrade`. [Source: docs/feature-flags.md, docs/working-with-v12.md]
- **v12 preview surface**: developed inside the v11 codebase behind `enable-v12-release`; has its own parallel Storybooks (`yarn storybook:v12`, separate ports) for `@carbon/react` and `@carbon/web-components`; v12 is also absorbing a subset of components from `carbon-for-ibm-products` directly into `@carbon/react`, shown with a "Migrated" badge in the v12 Storybook (not available in current published v11 package). [Source: docs/working-with-v12.md, docs/feature-flags.md]
- **TypeScript**: native `.d.ts` bundled with `@carbon/react` (`types: lib/index.d.ts` in package.json), but coverage is incomplete per the package README, which recommends `skipLibCheck: true` and points to a public GitHub Project tracking TS adoption. Not "@types/*"-based — types ship in-package.
- **Module output**: `@carbon/react` package.json declares `main: lib/index.js` (CJS), `module: es/index.js` (ESM), and a `sideEffects` array that whitelists `es/index.js`, `lib/index.js`, `src/index.js`, feature-flags entry points, and all `.scss`/`.css` files — meaning bundlers should be able to tree-shake JS but must respect the explicit sideEffects list for styles/feature-flags. [Source: packages/react/package.json via GitHub API]
- **SSR / Next.js / RSC**: no official Carbon statement found confirming or denying React Server Component compatibility; the community example repo `carbon-tutorial-next` demonstrates wrapping interactive Carbon components with `'use client'` in consumer code, implying Carbon itself relies on the consumer to draw the client/server boundary rather than shipping directives internally. Marked **unverified** as an official compatibility statement.
- **React 19**: allowed by current peerDependencies (`^19.0.0`), but two React-19-specific bugs (Tabs family breakage #18574, `use-resize-observer` incompatibility #19350) were reported and fixed in Feb/May 2025 — treat early React 19 adoption as having had a rocky start, now apparently resolved, though no dedicated "React 19 support" changelog entry was located to confirm full resolution scope.

## Customization hooks

- **`$prefix` (Sass config variable, default `cds`)**: overridable via `@use '@carbon/styles' with ($prefix: 'my-prefix')`; propagates to CSS class selectors and CSS custom-property names. [Source: docs/guides/sass.md]
- **Config variables** beyond `$prefix`: `$css--body`, `$css--font-face`, `$css--reset`, `$css--default-type`, `$font-display`, `$font-path` (set to `@ibm/plex` under Vite), `$use-akamai-cdn`, `$use-per-family-plex`, `$use-flexbox-grid`, `$flex-grid-columns` (default 16), `$css--emit-type-custom-props`. [Source: docs/guides/sass.md]
- **Per-component Sass imports**: every module in `@carbon/styles` can be `@use`d independently, e.g. `@use '@carbon/styles/scss/components/button'`, enabling a minimal custom entrypoint that mirrors the default one (`config` → `reset` → `grid` → `layer` → `themes` → `theme` → selected `components/*`). Sass modules can only be configured once per compilation unit; `@use '@carbon/styles';` (the "bring everything" form) must be the last `@use` if mixed with individual modules. [Source: docs/guides/sass.md]
- **Precompiled CSS**: `@carbon/styles/css/styles.css` path exists for consumers who don't want to run Sass at all (a past defect, #11599, was about this file missing from `sideEffects` breaking some bundlers — status of fix unverified from this pass).
- **CSS custom properties**: `$css--emit-type-custom-props` (default true) shows Carbon emits CSS custom properties for typography at minimum; broader "CSS custom properties for theming" behavior for colors/tokens is referenced across Carbon docs but was not independently verified line-by-line in this pass — **unverified in depth**.
- **Theming**: `@carbon/themes` supplies the named token sets (White/Gray 10/Gray 90/Gray 100, plus custom-theme support) that `@carbon/styles`/`@carbon/react` consume; React exposes a `<Theme>` component for scoping/switching themes at runtime.
- **Feature flags** (see Capabilities) are themselves a first-class customization/extension hook for consumers who want to adopt v12-bound behavior early or opt into preview behavior selectively.
- **Codemods**: `npx @carbon/upgrade migrate <codemod-name> --write` automates flag-driven and version-driven code migrations; not all flags have a codemod (Sass-only flags currently have none). [Source: docs/feature-flags.md]

## Known gaps, pitfalls, open issues (link issues)

- Sass build-time/bloat complaints, recurring over years, some predating the v10→v11 Sass-modules rewrite: [Should improve carbon compilation time #7294](https://github.com/carbon-design-system/carbon/issues/7294), [Sass is taking too long to compile #3348](https://github.com/carbon-design-system/carbon/issues/3348), [First compilation and live reload are too slow #6198](https://github.com/carbon-design-system/carbon/issues/6198), [global scss takes forever to build #5059](https://github.com/carbon-design-system/carbon/issues/5059), [discussion: How to improve carbon components SASS compile speed #8526](https://github.com/carbon-design-system/carbon/discussions/8526). Current relevance to `@carbon/react` 1.x/`@carbon/styles` 1.x (post Sass-modules) not independently re-verified — flag as **needs a fresh recency check** before assuming it's still an issue at current version.
- Tree-shaking/bundle-size concerns, also largely from the CommonJS/pre-modules era: [carbon-components is not amenable to tree-shaking #5980](https://github.com/carbon-design-system/carbon/issues/5980), [Package performance and bundle-size #4882](https://github.com/carbon-design-system/carbon/issues/4882), [Investigate tree-shaking opportunities #4881](https://github.com/carbon-design-system/carbon/issues/4881). `@carbon/icons-react` specifically recommends importing individual icons rather than the barrel to avoid pulling a large bundle.
- React 19 breakage (now closed): [Tabs/TabList/Tab/TabPanels/TabPanel broken with React 19 #18574](https://github.com/carbon-design-system/carbon/issues/18574) (closed 2025-02-14), [`use-resize-observer` does not support React 19 #19350](https://github.com/carbon-design-system/carbon/issues/19350) (closed 2025-05-20). Both closed, but indicate React-19 support required patching after the major React release rather than being ready at launch.
- Precompiled CSS `sideEffects` gap: [`@carbon/styles` should include `.css` in side effects #11599](https://github.com/carbon-design-system/carbon/issues/11599) — current `sideEffects` array in `packages/react/package.json` does list `**/*.css`, suggesting this was addressed for `@carbon/react`; status specifically for `@carbon/styles`'s own package.json not checked in this pass.
- TypeScript coverage gap is self-acknowledged by the Carbon team (README: "not all components have yet been typed"), with an open tracking GitHub Project ("TypeScript Adoption", `github.com/orgs/carbon-design-system/projects/53`) rather than a closed/finished state.
- IBM Telemetry is bundled by default in `@carbon/react` (opt-out, not opt-in) — a governance/privacy consideration for a downstream package that will itself be redistributed across multiple business-platform repos.
- No official, primary-source statement was found confirming React Server Components / Next.js App Router support status for `@carbon/react`; only third-party/community tutorials demonstrate the `'use client'` workaround pattern. Treat as **unverified**.

## Options for Afframe UI (option · consequence, one line each)

- Depend on `@carbon/react` (Layer 2) directly · gets styles + icons re-exported automatically, simplest dependency graph, but inherits its release cadence (biweekly minors) and its full component surface/bundle even if only a subset is used.
- Depend on lower-layer packages individually (`@carbon/styles`, `@carbon/icons-react`, `@carbon/themes`, etc.) and build components from `@carbon/react` selectively or from scratch · finer control over bundle size and versioning per package, but more integration/maintenance surface and manual re-implementation of what `@carbon/react` already wires together.
- Consume `@carbon/react` via its Sass module entrypoints (`@use '@carbon/styles/scss/components/<name>'`) instead of the bulk `@use '@carbon/styles'` · smaller compiled CSS and faster builds, but requires maintaining an explicit per-component import list that must be kept in sync as Afframe UI's own component set grows.
- Pin to a specific `@carbon/react` minor and adopt `enable-v12-*` flags selectively ahead of GA · earlier alignment with the eventual v12 default behavior and smoother future migration, but exposes Afframe UI to preview-status APIs that Carbon says are "fixed" but still pre-GA, and to a Storybook/testing setup split across v11/v12 surfaces.
- Wait for v12 GA before building on any v12-only behavior (stay on plain v11 defaults) · avoids preview-status risk entirely, but means a larger, un-staged migration whenever v12 eventually ships (no committed GA date exists as of retrieval).
- Re-export precompiled CSS (`@carbon/styles/css/styles.css`) instead of running Sass in Afframe UI's own build · avoids requiring Dart Sass/`@use` toolchain in every consumer repo (relevant given consumer stack is undecided), but loses the ability to override `$prefix`/config variables or tree-shake unused component styles at the Sass level.
- Vendor/wrap the `@carbon/react` TypeScript gaps with Afframe UI's own `.d.ts` overrides for untyped components · gives consumers of Afframe UI a fully-typed surface, but adds a maintenance burden to track upstream typing changes.
