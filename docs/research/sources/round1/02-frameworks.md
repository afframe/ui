# 02 · Framework implementations, Charts, IBM.com
Retrieved: 2026-09-23 · Lane: frameworks

## Summary (5-10 bullets)

- Carbon officially maintains two framework implementations only: `@carbon/react` and `@carbon/web-components`, both in the `carbon-design-system/carbon` monorepo. The monorepo README states explicitly: "Community-maintained packages are also available for Angular, Svelte, and Vue" — i.e. Angular, Vue, and Svelte are NOT core-team-maintained. [https://github.com/carbon-design-system/carbon]
- `@carbon/web-components` (v2.64.0) is a Lit-based custom-elements library. Its README documents an in-progress v3 that migrates from Carbon's own `carbonElement` decorator to Lit's native `customElement` decorator, and drops auto-registration on import (v3 requires explicit `defineCustomElement`). [https://github.com/carbon-design-system/carbon/blob/main/packages/web-components/README.md]
- Web Components ship React wrapper components (generated per-component, historically via `@lit/react`'s `createComponent`) so they can be dropped into a React tree without hand-writing wrapper code; SSR of those React wrappers has historically needed Node ≥12.16.3 for conditional-exports support, and plain custom elements do not server-render their shadow DOM content without a declarative-shadow-DOM strategy. [https://github.com/carbon-design-system/carbon-web-components/blob/main/docs/welcome-story-react.mdx] (older repo, pre-monorepo-merge; treat specifics as unverified against current v2/v3 code)
- Angular (`carbon-components-angular`), Vue (`@carbon/vue`), and Svelte (`carbon-components-svelte`) are separately maintained repos under the `carbon-design-system` GitHub org (not the `carbon` monorepo), each shipping components re-implemented natively for that framework rather than wrapping `@carbon/web-components`.
- `carbon-components-vue` (the pre-Vue-3, unscoped npm package) is dead: last publish 2022-04-12, version `0.0.1`, no license/repo metadata in the registry. The live package is `@carbon/vue` (v3.0.32, Vue 3-oriented, peer dep `vue: ^2.7.0` per npm metadata — worth re-verifying directly).
- Carbon Charts (`@carbon/charts`, D3 + TypeScript) ships framework wrappers for vanilla JS, React, Angular, Vue, and Svelte, with "26 charts" advertised in its README; per-framework wrapper packages update in lockstep with the core (all four wrapper packages plus core were republished the same day, 2026-09-16).
- Carbon Charts has open, unresolved accessibility gaps: multiple filed issues describe WCAG 1.4.1 "Use of Color" violations (e.g. MeterChart relying on color alone) and missing keyboard/screen-reader access to tooltip data. [https://github.com/carbon-design-system/carbon-charts/issues/2072, https://github.com/carbon-design-system/carbon-charts/issues/2054, https://github.com/carbon-design-system/carbon-charts/issues/65]
- Carbon for IBM.com (`@carbon/ibmdotcom-*`) is explicitly scoped to IBM.com: its README says "This library is an extension of the Carbon IBM Design System. It contains unique components shared between the IBM.com user journeys to unify its look and feel." `@carbon/ibmdotcom-react` has not published since 2024-10-24 (stale vs. the actively-published `-web-components`, `-styles`, `-services`, `-utilities` siblings, all republished 2026-09-23), suggesting the React package track has been deprioritized in favor of web-components + generated React wrappers.
- Carbon does not maintain an official Ember implementation; an `IBM/carbon-components-ember` repo exists under the separate `IBM` GitHub org (not `carbon-design-system`) and is out of scope for the primary inventory.

## Capabilities

- **React (`@carbon/react`)**: full first-party component set, deepest coverage; covered in depth in lane 1. Peer support: React 16.8.6–19.x. [https://www.npmjs.com/package/@carbon/react]
- **Web Components (`@carbon/web-components`)**: custom elements (`cds-*` tags), built on Lit; usable from any framework or vanilla HTML/JS; ships a CDN build; documents form-usage and custom-styling guides; no npm `peerDependencies` recorded in the inventory (framework-agnostic by design). Storybook: https://web-components.carbondesignsystem.com/. React usage is supported via generated wrapper components (historically `es/components-react`, built with `@lit/react`'s `createComponent`) so consumers get typed React components instead of raw JSX custom-element tags; this is the path for using Carbon inside React/Next.js without pulling in `@carbon/react`. SSR caveat (from the legacy `carbon-web-components` repo docs, pre-monorepo-merge, treat as **unverified for current v2/v3**): wrapper components required Node ≥12.16.3 conditional-exports support to run under SSR, and shadow-DOM content generally is not part of the server-rendered HTML unless declarative shadow DOM is used — meaning a Next.js app using raw custom elements (not the React wrappers) typically needs `dynamic(..., { ssr: false })` or client-only rendering for interactive components.
- **Angular (`carbon-components-angular`)**: native Angular component library (not a web-components wrapper), peer-pinned to `@carbon/styles ^1.54.0`; large active community (567★, monthly-ish releases visible in `pushed_at`).
- **Vue (`@carbon/vue`)**: native Vue implementation under the `carbon-design-system` org; current major is 3.x on npm, but the recorded `peerDependencies` in the inventory list `vue: ^2.7.0` — this is either stale metadata or an actual constraint; **flag as needing direct verification against the package's own README before consumer use**.
- **Svelte (`carbon-components-svelte`)**: largest star count of any non-React/WC implementation (2,909★), most recently pushed of the community set (2026-09-23), actively maintained by community lead `metonym` (visible across Charts and other Carbon-adjacent repos), with a companion ecosystem: `carbon-icons-svelte`, `carbon-pictograms-svelte`, `carbon-preprocess-svelte` (build-time optimizations e.g. stripping unused CSS).
- **Parity**: the Carbon monorepo has tracked "React|WC Parity" issues (e.g. issue #19931 "create `composed-modal`", pointing to a parent tracking issue #17326) indicating Web Components historically lagged React on some newer/composite components; community reporting describes an active 2023-era effort to bring Web Components to full parity with React, and by v2 the two are described as at "full parity with the latest version of @carbon/react" in community sources — **exact current parity state (any React-only or WC-only components today) could not be confirmed from primary sources in this pass; treat as open question**. [https://github.com/carbon-design-system/carbon/issues/19931]
- **Carbon Charts**: D3 + TypeScript rendering engine; core package advertises "26 charts" across bar, line, area, pie/donut, scatter, bubble, gauge, meter, boxplot, and combo variants (exact current count not independently re-verified per chart type in this pass — see Open questions); themed via Carbon design tokens (light/dark, White/Gray 10/Gray 90/Gray 100) so charts visually match a Carbon-based product; wrapper packages (`-react`, `-angular`, `-vue`, `-svelte`) are thin framework bindings around the same core rendering engine and are version/release-synced with core (all republished together on 2026-09-16).
- **Carbon for IBM.com**: `@carbon/ibmdotcom-web-components` (Lit-based, Custom Elements v1 + Shadow DOM v1) is the primary track and includes generated React wrappers in the same package; `@carbon/ibmdotcom-styles`, `-services`, `-utilities` are framework-agnostic helper packages (services = "ES6 Service classes", e.g. translation/locale/analytics integration tied to IBM's own backend services). The README frames the whole library as IBM.com-marketing-site-specific ("unify its look and feel" across "IBM.com user journeys"), not a general-purpose product design system.

## Customization hooks

- Web Components: CSS Shadow Parts and CSS Custom Properties are documented mechanisms for restyling components from outside the shadow boundary (per `@carbon/ibmdotcom-web-components` README table of contents: "Using CSS Custom Properties", "CSS Shadow Parts", "Creating derived components with different style").
- Web Components v3 (in progress) exposes an explicit opt-in registration API (`defineCustomElement`) and a "prefixed build"/"scoped registries" mechanism, letting a consumer register Carbon elements under a custom tag prefix — relevant if Afframe wants to avoid tag-name collisions with another design system or with multiple Carbon versions on one page. [https://github.com/carbon-design-system/carbon/blob/main/packages/web-components/README.md]
- Carbon Charts theming is driven by Carbon design tokens/themes, so retheming follows the same token-override mechanism as the rest of Carbon (see lane on theming/tokens) rather than a chart-specific API — **not independently re-verified against the charts.carbondesignsystem.com theming docs in this pass; the charts documentation site could not be fetched (JS-rendered SPA returned no usable static content to the fetch tool)**.
- Angular, Vue, Svelte implementations each expose their own component API surface (props/inputs, slots) independent of the React or Web Components APIs — there is no single cross-framework prop contract; a design-system layer that needs to add custom props/variants would need to do so per-framework-implementation, not once centrally, in the case of Angular/Vue/Svelte.

## Known gaps, pitfalls, open issues (link issues)

- Web Components v3 is a breaking migration in progress (branch `feat/web-components-v3`): importing a component's class file will no longer auto-register the custom element; consumers pinning to `@carbon/web-components` should watch for this majoradoption. [https://github.com/carbon-design-system/carbon/blob/main/packages/web-components/README.md]
- Carbon Charts accessibility: filed, open issues describe WCAG 1.4.1 (Use of Color) violations in MeterChart and other charts, and a long-standing (since 2018) request thread for proper screen-reader/ARIA support that the search summary describes as still not fully resolved. [https://github.com/carbon-design-system/carbon-charts/issues/2072] [https://github.com/carbon-design-system/carbon-charts/issues/2054] [https://github.com/carbon-design-system/carbon-charts/issues/65]
- `@carbon/ibmdotcom-react` has not published in ~2 years (last: 2024-10-24) while the rest of the `carbon-for-ibm-dotcom` package family publishes daily/weekly — a strong signal this track is deprioritized; do not assume feature-equivalence with `@carbon/ibmdotcom-web-components`.
- `carbon-components-vue` (old unscoped npm name) is dead (last publish 2022, version 0.0.1, no license recorded) — any tutorial or blog post referencing `carbon-components-vue` instead of `@carbon/vue` is almost certainly stale.
- React↔Web-Components parity has open tracked gaps in the Carbon monorepo issue tracker (e.g. #19931/#17326 for `composed-modal`); the current, complete list of any-still-missing components could not be enumerated from primary sources within this pass — see Open questions.
- Angular Charts wrapper (`@carbon/charts-angular`) peer-caps Angular at `< 16.0.0` per its published `peerDependencies` — this is materially behind current Angular major versions and is a real compatibility constraint for a new Angular consumer app, not just a documentation lag; needs re-verification against the package's actual `peerDependenciesMeta`/support statement before relying on the number.
- Vue Charts wrapper (`@carbon/charts-vue`) peer-caps at `vue ^2.7.0` (Vue 2) even though `@carbon/vue` (non-chart components) targets Vue 3 — a Charts + `@carbon/vue` combination on Vue 3 may hit a version mismatch; needs direct verification.

## Options for Afframe UI (option · consequence, one line each)

- **React-only foundation (build on `@carbon/react`)**: simplest integration and deepest component/feature coverage, but locks every future consumer repo into React; Angular/Vue/Svelte consumers would need either a rewrite or a second design-system track.
- **Web-Components foundation (build on `@carbon/web-components`)**: framework-agnostic — usable from React (via generated wrappers), Angular, Vue, Svelte, or plain HTML — at the cost of the component set being (per open parity issues) potentially a step behind `@carbon/react` on the newest/composite components, plus SSR needing extra handling (declarative shadow DOM or client-only rendering) for frameworks like Next.js.
- **Hybrid (Web-Components core + thin React layer for the current React-heavy consumer)**: matches "consumer stack undecided" by keeping the underlying implementation portable while giving the nearest-term (React/Next.js-likely) consumer idiomatic React ergonomics via the wrapper mechanism Carbon itself ships — but doubles the surface Afframe UI has to test (raw custom elements + React wrapper behavior).
- **Adopt Carbon Charts as-is for any data-viz needs**: gets 26 chart types and multi-framework wrappers for free, themed to Carbon tokens, but inherits its open accessibility gaps (color-only encoding, tooltip/keyboard/screen-reader access) — Afframe UI would need to either patch/wrap charts for accessibility or document the gap for consumers.
- **Treat Carbon for IBM.com as reference only, not a dependency**: its components/services are built for ibm.com's own marketing-journey needs (IBM-specific services like locale/analytics integrations) and its React track is stale; using it as a direct dependency risks pulling in IBM.com-specific assumptions and an unmaintained React path — copying patterns rather than depending on the package is the lower-risk route, with no claim made here about which is better.
