# L · Labs treatment (non-React packages)
Retrieved: 2026-09-24

## Summary

Of the 36 published `@carbon-labs/*` packages in `labs-tech.json`, 18 are React (confirmed via `react`/`react-dom` peers, repo path `packages/react/src/components/*`, or unpacked source using React hooks) and 18 are non-React: 9 are `@carbon/web-components`/Lit custom elements ("wc-*" plus the unprefixed AI experiments and `network-graph`), and 2 are framework-agnostic/tooling (`primitives`, `vscode-snippets`). The repo (`labs-repo-names.txt`) also holds 3 private, unpublished web-component source packages (`wc-ai-feedback`, `wc-network-graph`, `wc-ai-ux-control`) that correspond to dead published packages from an older repo layout, plus two example-only directories (`first-time-orientation`, `toolbar`) with no matching core source package found anywhere in the tree.

Applying Hleb's Labs rule ("if they are web-components only... rebuild or adaptation"; "if something overlaps with Labs, and Labs are not React, then we better use what overlaps than rebuild Labs to React"): of the 9 live WC-only packages, 2 have full functional overlap with an already-included React component (`wc-empty-state` -> IBM Products EmptyState family; `wc-date-picker` -> `@carbon-labs/react-date-picker`/core DatePicker), so the rule points to using the React side and treating the WC package as out-of-scope even though it exists. The remaining 7 live WC-only packages (`wc-ai-tag`, `wc-global-header`, `wc-wysiwyg`, `wc-resizer`, `wc-style-picker`, and the two private ones once published, `wc-ai-feedback`/`wc-network-graph`) have partial or no React overlap and fall into the wrap-or-rebuild decision this file lays out. All dead/scaffold/deprecated/superseded packages (12 of the 36) stay excluded regardless of tech, matching scope.md section 4 policy already applied to the rest of Labs.

## Overlap analysis (per live non-React package)

### `wc-empty-state` vs IBM Products EmptyState family (I23) - overlap: full
`wc-empty-state`'s own package exports one `empty-state` custom element with bundled illustration assets for error, no-data, no-tags, not-found, notifications and unauthorized states (`es/components/empty-state/src/assets/*-illustration.js`, seen in the unpacked tarball). IBM Products already ships one dedicated React component per exact same state: `EmptyState`, `ErrorEmptyState`, `NoDataEmptyState`, `NoTagsEmptyState`, `NotFoundEmptyState`, `NotificationsEmptyState`, `UnauthorizedEmptyState` (catalog section 4.1, I23). The state-by-state naming match (error / no-data / no-tags / not-found / notifications / unauthorized) is a one-to-one feature overlap. Rule -> use the IBM Products React family; no wrap or rebuild needed for `wc-empty-state`.

### `ai-tag` and `wc-ai-tag` vs `@carbon/react` AILabel (I16) - overlap: partial
`wc-ai-tag` (`labs.status: "draft"` in its own package.json) renders a single custom element `<clabs-tag>`-style component described as "Carbon for AI - tag component" with a bundled `@lit/react` wrapper (`es/react/tag.d.ts` exporting `CLABSTag`). `@carbon/react` AILabel/AILabelActions/AILabelContent (I16, catalog section 2.1) provides the standard Carbon "AI-generated content" badge/tooltip/actions pattern used across the design system. Both mark AI-touched content, but AILabel is a badge-plus-popover pattern attached to a host element, while `wc-ai-tag` is a standalone tag/chip variant (a `Tag`-family shape) tuned for AI labeling in table cells or lists - a different visual form for an overlapping purpose (signal "this content involved AI"). Where the need is the standard AI-content badge, AILabel already covers it (use it, no rebuild). Where the need is specifically an AI-flavoured tag chip (not a badge), there is no React equivalent in scope; this residual is the wrap-or-rebuild candidate, and it is Labs `draft` status, the least mature tier.

### `ai-feedback` vs `@carbon/ai-chat` feedback features (O9) - overlap: not directly comparable (package dead)
`ai-feedback` 0.12.0 is dead (last published 2024-06-27) and its source has moved to the private, unpublished `wc-ai-feedback`. `@carbon/ai-chat` 1.21.0 (already included, O9) ships its own thumbs-up/down and feedback-collection UI as part of the chat surface (per its documented feature set; not independently re-verified in this pass - unverified detail level). Because the Labs package is not currently available (dead publish, unpublished successor), there is nothing to wrap or rebuild today; the feedback need inside an AI chat context is already served by `@carbon/ai-chat`'s own feedback UI. Recommendation: do not build against `ai-feedback`/`wc-ai-feedback` until IBM republishes it; re-run this comparison then.

### `wc-global-header` vs `@carbon/react` UI Shell Header (I13) and `@carbon-labs/react-ui-shell` (I37) - overlap: partial
`wc-global-header` ships a prebuilt React entry point (`es/wc-global-header-react.mjs`) in its own package, meaning IBM itself already builds a React-consumable wrapper for it - evidence the WC and React worlds are not drop-in equivalent (a wrapper is needed even by the publisher). `@carbon/react`'s UI Shell Header (I13) is the stable app-shell header (logo, nav, actions, hamburger). `@carbon-labs/react-ui-shell` (I37) is Labs' own React alternative shell. The functional core (global top bar, product name, nav slot) overlaps across all three; `wc-global-header`'s Labs-specific extras (its own theming/config surface, not enumerated here in detail - unverified) are the residual gap. Rule -> use the core UI Shell Header or `react-ui-shell` (both already React and included); treat any `wc-global-header`-only feature as an "Improve" item to confirm against the two React shells before considering a wrap.

### `wc-wysiwyg` vs anything in scope - overlap: none
`wc-wysiwyg`'s README (unpacked from the published tarball) describes a full rich-text editor built on TipTap: bold/italic/underline/strikethrough, six heading levels, bullet/numbered/task lists, tables with merge/split, text alignment/color/highlight via Carbon tokens, in-editor search, code blocks/blockquotes, link/image insertion with resizing, HTML/Markdown source toggling, undo/redo. No component in `@carbon/react`, IBM Products, or the included Labs React set (I37-I50) provides rich-text editing. Overlap: none. This is a clean wrap-or-rebuild candidate.

### `network-graph` vs Carbon Charts and ECharts graph series (O22) - overlap: potentially full, but package is dead
`network-graph` 0.9.0 is dead (last published 2024-06-27, old `repository.directory`). Its successor `wc-network-graph` is private/unpublished. Node-link/network graph visualization is a standard chart type; Apache ECharts (themed via `@carbon/echarts-theme`, O22, already included) natively supports `graph` series type, and Carbon Charts' maintained roadmap covers common chart types. Because Labs' own network-graph component is dead and its replacement unpublished, the practical path today is the ECharts `graph` series with the Carbon theme, not the Labs package. Overlap assessment: likely full once compared feature-by-feature, but moot while the Labs side is unavailable.

### `wc-date-picker` vs `@carbon-labs/react-date-picker` (I38) and core DatePicker - overlap: full
`wc-date-picker`'s source tree includes `adapters/web-component-adapter.js` and the same `date-picker`, `date-picker-input`, `date-picker-input-skeleton`, `calendar-renderer` module set that `@carbon-labs/primitives`' `date-picker` state machine backs (the primitives package explicitly exposes a `./date-picker` subpath with the Temporal-based state machine: `actions`, `effects`, `guards`, `states`, `temporal-utils`). `@carbon-labs/react-date-picker` (I38, already included, v12-stable milestone graduates it to core) is built on the same underlying primitives for the React side. Both are the same date-picker generation (Temporal-based, replacing the legacy flatpickr DatePicker) delivered through two renderers. Overlap: full. Rule -> use `react-date-picker`; no wrap or rebuild.

### `wc-resizer` vs `@carbon-labs/react-resizer` (I9) - overlap: full
`wc-resizer`'s README lists the same four-part model as the React Resizer: a grid container, individual panels, a drag handle, and a corner pivot handle, in both declarative (HTML-only) and composable (JS-driven, explicitly "frameworks like React can handle resizing logic via JavaScript") modes. `@carbon-labs/react-resizer` (I9) is already an `@carbon/ibm-products` dependency and on the v12 migration list. Overlap: full. Rule -> use `react-resizer`; no wrap or rebuild.

### `wc-style-picker` vs `@carbon-labs/react-style-picker` (I42) - overlap: full
Both packages expose the same component set by name: `style-picker`, `style-picker-sections`, `style-picker-color`, `style-picker-group`, `style-picker-icon`, `style-picker-option`, `style-picker-section`, sharing a `style-picker-context`. This is a one-to-one structural match between the WC and React builds (same design, two renderers), consistent with `@carbon-labs/react-style-picker` (I42, already included) being the intended primary implementation. Overlap: full. Rule -> use `react-style-picker`; no wrap or rebuild.

### `@carbon-labs/ai-chat` vs `@carbon/ai-chat` (O9) - overlap: full, but by design (superseded, not "use the overlap")
Carbon catalog section 5 states directly: "`@carbon-labs/ai-chat` chat (WC) ... superseded for React by `@carbon/ai-chat` (distinct project, V row 8a)". This is not a same-generation overlap case (two renderers of one design) like the style-picker/resizer/date-picker pairs above; it is an older Labs prototype replaced by a separately maintained, already-included React-capable product (`@carbon/ai-chat` ships its own React entry point and is O9 in scope.md). Treatment: out, use `@carbon/ai-chat`.

## Wrap or rebuild: options and consequences

Applies to the packages with no full React overlap: `wc-wysiwyg` (no overlap), `wc-ai-tag` (partial, residual AI-chip form), `wc-global-header` (partial, residual global-header-only features), and, if/when republished, `wc-ai-feedback`/`wc-network-graph`/`wc-ai-ux-control`.

| Option | Extra runtime / version caps | SSR | Theming | Events / TypeScript | Bundle size | Maintenance on Labs updates | Apache-2.0 section 4 |
|---|---|---|---|---|---|---|---|
| (a) React 19 native custom-element support | Still requires `lit` + `@carbon/web-components` 2.x at runtime (the custom element itself is unchanged); React 19 only removes the need for a wrapper library on the consuming side. `@carbon/web-components` has no 3.x on npm (latest 2.64.0, per ground truth), so this caps that dependency below the v12-stable WC v3 milestone until upstream ships it. | Custom elements render on the server as opaque tags unless the element itself implements Declarative Shadow DOM; React 19's native support covers passing props/attributes through, not SSR hydration of the shadow tree. Next.js SSR/RSC support for custom elements is still evolving (react.dev notes native support is new; DSD behaviour is browser/element-dependent) - treat as (unverified) per-element. | Shadow-DOM encapsulated; Carbon tokens cross the boundary via `--cds-*` custom properties (inherited through shadow DOM by design), so theming works if the element consumes the same tokens as `@carbon/styles`, but component-level style overrides via CSS classes do not cross the boundary. | React 19 passes props as HTML attributes/properties per its custom-element interop rules; complex data (objects/arrays) needs property (not attribute) binding, which native JSX handles differently from `@lit/react`; no first-party generated TypeScript prop types - consumer writes/derives its own. | No wrapper library added; element's own JS/CSS (Lit ~5-7kB gzip typically, plus `@carbon/web-components` shared chunk) ships regardless of which option is chosen. | Zero wrapper-maintenance overhead; breaking changes in the custom element's attribute/event contract still break the integration and must be tracked on every Labs release. | None, if the element is consumed as-is (no Labs source copied). |
| (b) `@lit/react` `createComponent` wrapper | Adds `lit` (already a Labs peer for `wc-resizer`; transitive for `@carbon/web-components`-based ones) and `@lit/react` (`@carbon/ai-chat` already uses `@lit/react ^1.0.6` per ground truth, so the pattern is already present in the included tree). Same `@carbon/web-components` <3.0.0 cap as (a). | Same SSR limits as (a): the wrapper only changes the React-side integration, not whether the underlying element supports DSD/server rendering. `@lit/react`'s `createComponent` is a client-side factory; using it inside a Next.js Server Component boundary requires marking the wrapper `"use client"`. | Same shadow-DOM/`--cds-*` boundary as (a); `createComponent` lets you map named DOM events to React event props and pass complex props/properties correctly (its main advantage over native JSX attribute-only binding). | `createComponent` gives typed React props/events when the underlying element and TS types are well-typed (two of the target packages, `wc-ai-tag` and `wc-global-header`, already ship a prebuilt React wrapper this way, per unpacked tarballs); reduces attribute/property mismatches vs (a). | Adds `@lit/react` (small, no vdom) on top of the element's own bundle; marginal over (a). | Wrapper code is thin and generated per component; still needs re-verification against Labs' semver-0.x breaking changes (all Labs packages are 0.x, no stability guarantee) on every bump. | None if only the compiled element is imported; if the wrapper is hand-copied/adapted from Labs' own `es/react/*.d.ts` source rather than imported from the package, Apache-2.0 section 4(a)-(d) applies: must retain copyright/license notices, state changes made, and cannot imply IBM endorsement. |

Notes:
- `wc-ai-tag` and `wc-global-header` already ship IBM-authored React wrappers built with `@lit/react` inside their own published packages (`es/react/tag.d.ts`, `es/wc-global-header-react.mjs`), which is direct evidence that option (b) is the path IBM itself uses for these two, ahead of any option (c) rebuild.
- `wc-wysiwyg` has no such prebuilt wrapper in the unpacked tarball; option (b) would need a wrapper written in-repo (still no Apache-2.0 obligation if only the compiled TipTap-based element is imported and used unmodified through `createComponent`).
- v12-stable milestone (2027-03-31, per ground truth) is when Carbon's own roadmap targets WC v3; today's `@carbon/web-components` <3.0.0 cap under options (a)/(b) sits below the "full v12" surface the v12 rule asks for, so this cap is time-bound, not permanent, similar to the `@carbon/ai-chat` cap already accepted for O9.

## Mapping Hleb's rules to the options

D1 ("React only") is a constraint on option selection, not a ban on consuming a custom element: options (a) and (b) both keep the product surface React (JSX components with React props/events), even though a non-React runtime (Lit, `@carbon/web-components`) still executes under the hood; option (c) removes that runtime dependency entirely and is the only option with zero non-React code shipped. The v12 rule ("full v12... except if it breaks some component we need") interacts with the `@carbon/web-components` <3.0.0 cap shared by (a) and (b): that cap does not block `@carbon/react` v12 itself (a separate package), but it does mean the wrapped Labs element stays on WC 2.x until IBM ships WC v3 (targeted for the v12-stable milestone), which is the same kind of temporary, named exception the v12 rule already allows for `@carbon/ai-chat` (O9). The Labs rule text quoted in the brief directly names this three-way choice ("rebuild or adaptation with dependencies, what is correct idk" for WC-only Labs, and "use what overlaps than rebuild Labs to React" when a React overlap exists) and defers the wrap-vs-rebuild call per package rather than setting one default; the per-package overlap findings above (full overlap -> use the React sibling; partial/no overlap -> choose among (a)/(b)/(c) with the consequences in the table) are the inputs that rule needs, without a single global pick.
