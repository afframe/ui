# Chat elements

<SourceLabel name="afframe" />

[Source code](https://github.com/afframe/ui/tree/main/src/components/ChatElements). See also [Carbon AI Chat docs](https://chat.carbondesignsystem.com/tag/latest/docs/documents/Overview.html).

A renderer for `user_defined` items of IBM's AI chat (`@carbon/ai-chat`):
a chart drawn by Carbon Charts or ECharts, which the chat has no item type
for. `ChatChart` also works on its own, outside a chat. Both are client
modules.

Carousels, tables and code render natively in `@carbon/ai-chat`, so Afframe
has no renderer for them: send a `carousel` item
([`CarouselItem`](https://chat.carbondesignsystem.com/tag/latest/docs/interfaces/Type_reference.CarouselItem.html)), or a
markdown table or fenced code block in a `text` item (the chat's markdown
renderer sorts, filters and pages tables and highlights and copies code). See
the [message format](https://chat.carbondesignsystem.com/tag/latest/docs/documents/Server_communication.Message_format.html)
and the [markdown options](https://chat.carbondesignsystem.com/tag/latest/docs/interfaces/Type_reference.ChatContainerPropsMarkdown.html).

## Wiring

Pass `renderChatElement` as the chat's `renderUserDefinedResponse`:

```tsx
'use client';
import { ChatCustomElement, renderChatElement } from '@afframe/ui';

<ChatCustomElement
  className="assistant"
  messaging={{ customSendMessage }}
  renderUserDefinedResponse={renderChatElement}
/>;
```

It draws items whose `user_defined.user_defined_type` is one of
`chatElementTypes` (`afframe-chart`) and returns `null` for any other item,
so an app chains its own renderer after it:

```tsx
const render: RenderUserDefinedResponse = (state, instance) =>
  renderChatElement(state, instance) ?? renderMyElement(state);
```

The third argument takes `elements` (the types to draw, default all) and
`messages` (`{ chart }`, a partial of the chart's messages).

## Payloads

A server sends a `user_defined` item. Every payload is JSON and passes a
runtime guard (`isChatChartData`) before it renders.

```json
{
  "response_type": "user_defined",
  "user_defined": {
    "user_defined_type": "afframe-chart",
    "chart_type": "bar",
    "title": "Revenue by region",
    "summary": "Prague 2,000; Brno 1,400.",
    "data": [
      { "group": "Prague", "value": 2000 },
      { "group": "Brno", "value": 1400 }
    ]
  }
}
```

| `user_defined_type` | Payload                                                                                                                                          | Engine        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------- |
| `afframe-chart`     | `{ chart_type: 'bar' \| 'line' \| 'area' \| 'pie' \| 'donut' \| 'scatter'; title?; summary; data: { group; key?; value }[]; engine?: 'charts' }` | Carbon Charts |
| `afframe-chart`     | `{ engine: 'echarts'; title?; summary; option: object }` (a subset, below)                                                                       | ECharts       |

- Chart: `summary` is required, it is the text alternative. `data` is
  Carbon Charts tabular data: `group` is the series or slice, `key` the x
  value of line, area, scatter and grouped bar charts. `group` and `key` must not
  contain `<` or `>` (Carbon Charts tooltips render them as HTML); in the
  Carbon Charts title they are dropped. A bar chart without
  `key` draws one bar per group. Vega-Lite specs, the format of the Carbon
  Labs chart element, are not accepted.
- ECharts: the payload is untrusted, so only this subset of the option
  reaches ECharts; every other key is dropped:
  - `title` (one or a list): `text`, `subtext`.
  - `legend`: `show`, `orient`, `data` (strings).
  - `grid`: `left`, `right`, `top`, `bottom`, `containLabel`.
  - `xAxis`, `yAxis` (one or a list): `type`, `name`, `data`, `min`, `max`,
    `boundaryGap`.
  - `dataset`: `source` (rows of strings, numbers and `null`), `dimensions`.
  - `tooltip`: `trigger`, `axisPointer.type`; it always renders on the canvas
    (`renderMode: 'richText'`).
  - `series` (one or a list) of type `bar`, `line`, `pie` or `scatter`:
    `name`, `data` (values, value lists or `{ name, value }`), `stack`,
    `smooth`, `radius`, `center`, `xAxisIndex`, `yAxisIndex`,
    `datasetIndex`, `encode`, `areaStyle.opacity`.
  - `animation`.

  Dropped on purpose: title links and targets, formatters, rich text,
  labels, symbols (`image://`), background images, `baseOption`, `media`,
  `options` and `timeline`.

- `ChatChart` takes `animations` (default `true`) besides the payload, for
  screenshots.

## Loading

Each engine loads with `import()` of its family's module when an element
first renders, behind a skeleton. A route that imports `ChatElements` ships
none of the Carbon Charts or ECharts code in its script tags; the engine
arrives as an async chunk when a message needs it. A Carbon Charts
figure carries `data-afframe-extra="charts"` and needs `@afframe/ui/charts.css`
imported by the app (the Charts page); ECharts renders inside its
`data-afframe-extra="echarts"` container. If an engine's code fails to load, the element
shows an inline error (`loadError`); the next element that needs it tries
the import again.

## States

- Streaming: until the item is complete (`messageItem` unset, `partialItems`
  present), an element type of this module shows a skeleton with
  `aria-busy="true"` and the `loading` message.
- Invalid payload: an inline error with `invalid(type)`; raw data is never
  shown. `renderChatElement` passes only the payload fields of each type to
  the component, so a payload cannot set `className` or `messages`.
- Engine errors: each element sits behind its own error boundary. A failed
  engine import shows `loadError` (the next element that needs the engine
  imports it again); an engine that throws while drawing (such as ECharts on
  an option it cannot draw, like a line series without axes) shows
  `invalid(type)`. Other elements in the chat keep rendering.

## Messages

Function messages are overridden from a client component (or use string
overrides in server code). The chart also takes the shared keys of
`ChatElementsMessages`: `loading` ("Loading"), `invalid(type)` ("This
content could not be shown."), and `loadError` ("This content could not
load. Reload the page to try again.").

| Element     | Key                 | Default                 |
| ----------- | ------------------- | ----------------------- |
| `ChatChart` | `chartLabel(title)` | the title, else "Chart" |

## Keyboard and screen reader behaviour

- Chart: a `figure` named by the title (`chartLabel`) and described by
  `summary` (visually hidden text, `aria-describedby`). No tab stop: no
  toolbar, and the legend does not filter. Carbon Charts keeps its own roles
  inside (title heading, legend group, labelled bars and slices). ECharts
  draws on a canvas; the figure's name and description are its text.
- Every control is at least 24 px (axe `target-size` runs on every story).

## Comparison with Carbon Labs AI chat

Checked on 2026-10-07: `@carbon-labs/ai-chat` 0.39.0 (every folder of
`es/components/`, the element sources `src/*.js` and templates) against
`@carbon/ai-chat` 1.22.0 (`MessageResponseTypes`, the `GenericItem` union in
the server entry types, and the compiled response dispatch) and
`@carbon/ai-chat-components` 1.12.0 (the markdown renderer). Labs elements
take their content as strings (JSON or text) on custom elements.

`@carbon/ai-chat 1.22` column: `native item type X`, `markdown renderer`,
`user_defined` or `none`. Result: `Afframe renderer`, `native, not built`,
