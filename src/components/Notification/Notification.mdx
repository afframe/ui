## Overview

There are 4 different types of notification components:
`ActionableNotification`, `InlineNotification`, `ToastNotification`, and
`Callout`. This page shows the one it documents; each section below links to
the page of the others.

<Canvas />

### ActionableNotification

`ActionableNotification` should be used when user action is required. It can
include an action, other interactive elements or rich text. It uses Toast-like
styling by default, but if you'd like it to be visually similar to an
InlineNotification, you can use the `inline` prop. If `actionButtonLabel` is not
provided, an action button will not be rendered. This component grabs and traps
focus until the action is acted upon or the notification is dismissed.

### InlineNotification and ToastNotification

`InlineNotification` and `ToastNotification` can not contain interactive
elements or rich text. These are announced by screenreaders when rendered. They
don't grab focus. Use them to provide the user with an alert, status, or log.

### Callout (previously StaticNotification)

`Callout` is non-modal and should only be used inline with content on the
initial render of the page or modal because it will not be announced to
screenreader users like the other notification components.

As such, this should not be used for real-time notifications or notifications
responding to user input (unless the page is completely refreshing and bumping
the users focus back to the first element in the dom/tab order). If a Callout is
rendered after the initial render, screenreader users' focus may have already
passed this portion of the DOM and they will not know that the notification has
been rendered until they circle back to the beginning of the page.

This is the most passive notification component and is essentially just a styled
div. If you place actions or interactive elements within this component, place
an `aria-describedby` on the interactive element with a value that matches the
`titleId` prop.

### Using the `role` prop

ActionableNotification's `role` prop allows you to provide a different
`aria-role` than the default, `alertdialog`.

This prop should be used with caution as it will disable the focus wrapping
required for `alertdialog` . Before using this prop, consider using `Callout`
instead.

For ActionableNotification to remain accessible when using this prop, you'll be
responsible for implementing a strategy to fulfill the needs of a screenreader
user. Two viable options include:

- Rendering notifications into an existing region that can immediately be
  navigated to via a hotkey. Once the user navigates there and takes an action
  or gets to the last focusable element, focus returns from the region to the
  element previously focused before they entered the region.
- Collecting notifications in a persistent place in the app (a "drawer" or "side
  panel") and announcing to the user how they can navigate to that place to
  review all notifications and optionally take action on it.

### Focus

On mount, an `ActionableNotification` with the default `alertdialog` role and
`hasFocus` moves focus to an action button. Carbon finds that button with a
query over the whole document, so it is the first action button on the page,
which may belong to another notification. Keep one alertdialog notification on
screen at a time.

Carbon runs that focus step after every render of the notification, not only
on mount. A re-render while it is open, from a parent state change or a prop
change, pulls focus back to the action button, even after the user moved it
elsewhere. To avoid it, render the notification through a small component that
mounts with it and turns `hasFocus` off after the first focus. The focus trap
does not depend on `hasFocus`. After Close, Carbon returns focus nowhere, so it
falls to the page body; return it to the control that opened the notification:

```jsx
function FocusOnceNotification(props) {
  const [hasFocus, setHasFocus] = useState(true);
  useEffect(() => setHasFocus(false), []);
  return <ActionableNotification {...props} hasFocus={hasFocus} />;
}

const notification = open && (
  <FocusOnceNotification
    onClose={() => triggerRef.current?.focus()}
    {...props}
  />
);
```

The state must live in that component, not in a page that stays mounted:
there, `hasFocus` is already `false` when the notification appears, and it
never takes focus.

`InlineNotification` does not take focus. After Close, focus falls to the page
body; move it back to a sensible place in `onClose`, such as the control the
message is about.

their stacking. As with `InlineNotification`, focus falls to the page body after
Close, so return it in `onClose`.

## NotificationActionButton and NotificationButton

These are the action and close buttons Carbon's notifications render. Use them
only to build a custom notification that looks and behaves like Carbon's.
`NotificationActionButton` takes `inline` for the inline look;
`NotificationButton` takes `notificationType` (`toast`, `inline` or
`actionable`) and an `aria-label`, `close notification` by default.
